# 洞察报告 v1：评测 Code Agent 时，什么真的在起作用

**日期**：2026-08-06　**范围**：本项目全部实测，样本均为小样本，每条结论后附其边界
**读者**：需要决定"自研 Code Agent 往哪走"和"如何判断它是否变好了"的人

---

## 0. 一句话

**本项目最可复现的发现不是关于 agent 的，是关于测量的：评测系统的缺陷几乎总是朝"结论更好看、更干净、更显著"的方向失败。** 它们不崩溃，它们产出一个可以写进报告的数字。二十个缺陷里，没有一个是靠程序报错发现的。

对产品的直接含义：**一个 Code Agent 团队最先需要的不是更多 benchmark，而是能证伪自己 benchmark 的机制。**

---

## 1. 什么在区分 Code Agent —— 不是模型

### 1.1 模型阶梯几乎不产生区分度，预算产生

同一批 case 上：

| 变的是 | 观测到的差距 |
|---|---|
| 模型（阶梯换档） | 0.16 |
| **预算（收紧 wall-clock）** | **0.85** |

而且两个反直觉的性质：

- **模型会适应预算而不是消耗预算。** 给多少用多少不成立，所以"当前用了多少 headroom"预测不了收紧后的表现。
- **曲线是悬崖不是斜坡。** 中间档位很窄，跨过去就整体塌陷。

**产品含义**：把 Code Agent 的能力宣称与延迟预算绑定发布。脱离预算的"成功率"数字不可比，也不可复现。

### 1.2 同一模型下，scaffold 决定单位时间产出

glm-5.2，120s wall clock（唯一四个框架都以相同方式执行的预算）：

| framework | 到达编辑阶段前的行为 | 结果 |
|---|---|---|
| Claude Code | 14.6 次工具调用 / 24.1 模型轮次 | 把时间花在推理上 |
| MiniAgent | 34.3 次工具调用 / 18.8 模型轮次 | 把时间花在动作上 |
| **Cline** | 6–13 次调用，**16/16 全部超时，15/16 尚未做出任何改动** | 120s 内到不了编辑阶段 |

**Cline 的 0.00 不是能力判断，是延迟判断**——它最快的一次完成需要 188s，多数需要 400s+。把它写成"Cline 得分为零"是错的。

**产品含义**：**scaffold 的首要设计变量是"多快开始动手"**，不是工具有多丰富。在紧预算下，推理密度是负债。

## 2. 失败模式是结构化的，不是随机的

三种失败在不同模型、不同框架上**可复现地重演**：

| 失败模式 | 表现 | 实测 |
|---|---|---|
| **在症状处设防** | 病根在下一层，却在报错的模块里加防御 | `long-order-snapshot`：GLM-4.5-air 3/3 改 `orders.py`，正确答案在 `cart.py` |
| **逐 caller 打补丁** | 不找共享原语，挨个修调用方 | `long-release-accounting`：3/3 改 3–4 个文件，上限是 2 |
| **盲目收敛** | 读得多、改得少、时钟到点仍在探索 | `long-cascade-reservation`：v3 拿到 10–14 轮、**一次都没改过文件** |

这三种都**不是随机错误**——同一模型+框架组合会稳定重现同一种。

**产品含义**：failure taxonomy 值得做成产品级能力。它们可枚举、可检测、可回归，比"成功率下降了"有用得多。

## 3. 测试投机：第一次在开放写入面上的读数

JD 点名"测试投机"。本项目此前所有投机检出率都是**零**，且必须附带一句"这是执行策略不是行为"——因为自建 suite 的 harness 一律禁止改测试，零值反映的是禁令。

真实 SWE-bench 实例**没有** `forbidden_paths`，三个框架都不受限。结果：

| framework | 编辑了 oracle 自己的测试文件 |
|---|---|
| Cline | **2/3** |
| Claude Code | **1/3** |
| MiniAgent（自研） | **0/3** |

Cline 那条 `resolved` 之所以仍然成立，**只因为 harness 在评分前还原了 oracle 文件**。没有这一步，它就是拿自己写的测试给自己打分。

**边界**：9 次尝试，撑不起任何比率。这是"存在性观测"不是"发生率"。要做成带区间的数字需要 6–8 个实例 × 各 2 次（已记录为待办 F3）。

**产品含义**：**投机不是罕见边缘情况，是默认倾向之一。** 任何把"测试通过"当作奖励信号的训练或评测流程，都必须假设写入面开放时模型会去动它。

## 4. 能力不等于会被使用

**ScratchPad 建好了、注册了、提示词写了、消融开关接了——模型在 24 个 trial 里只用了 3 次，且全在多轮场景。**

它声明的另一半用途是"熬过上下文压缩"。把预算收到 8k 强制压缩后：

| 配置 | compaction | scratchpad 使用 |
|---|---|---|
| 8k，无预警 | **9/9 触发** | **0/9** |
| 8k，**加压缩前预警** | 9/9 | **9/9** |

根因：`[context compacted]` 这条消息是在**丢失之后**才注入的。要靠记忆保住信息必须在压缩**之前**写，而模型对"正在逼近上限"没有任何信号——它只知道刚丢过一次。

**产品含义**：给 agent 加能力时，**同时要给它触发该能力的时机信号**。没有触发信号的能力在评测里等于不存在，而它的成本照付。

## 5. 一个我自己掉进去的坑：为不存在的差异构建解释

这一节原本的标题是"能力可以是净成本"。**它被后续测量推翻了，保留在这里因为犯错的过程比结论有用。**

### 观察到的现象

V3 比 V2 多了 planner、scratchpad、上下文管理。120s 下 V3（0.500）**低于** V2（0.625）。三组消融（各 8 case × 2 repeats）：

| arm | Task | 截断 | compaction |
|---|---|---|---|
| **v3 −context** | **0.812** | 关 | 关 |
| v3 @8k | 0.688 | 开 | **开，41 次** |
| v2（对照） | 0.625 | 关 | 关 |
| v3 @32k 默认 | 0.500 | 开 | **0 次** |
| v3 −planner−scratchpad | 0.438 | 开 | 0 次 |

### 第一个假设被推翻

我算出 V3 系统提示词大一倍、每轮慢 17%、同样时间少拿 6 轮，判断代价是"开销"。消融掉 planner+scratchpad 后是 **0.438，更低**。开销不是代价所在。

### 第二个假设也被推翻

于是我改判为"截断的代价一直付、压缩的收益从不兑现"，并据此把截断改成按压力触发。重跑：

| | Task | 截断中位/trial |
|---|---|---|
| v3 旧（无条件截断） | 0.500 | **1.0** |
| v3 新（按压力截断） | **0.5625** | **0.0** |

**截断的中位数本来就只有 1 次/trial。** 去掉它，分数几乎没动，仍远低于 `−context` 的 0.812。

### 然后我才去数机制

120s / 32k 下，上下文管理实际做的全部事情是：

| 动作 | 实测发生次数 |
|---|---|
| 测量 `observe()` | 每轮（无行为影响） |
| 截断 | **1 次/trial** |
| 压缩前预警 | **0** |
| 压缩 | **0** |

**没有任何机制剩下来能解释 4 个 trial 的差距。** 而 10 个配对检验本来就**无一通过 Holm 校正**（最强 raw p=0.039 → 0.391）。

### 真正的教训

我为一个**既无机制、也未通过显著性检验**的差异，连续构建了两个解释，并按第二个解释改了代码。这正是本报告 §0 和 §7 警告的那件事——只不过这次的受害者是我自己：**数字看起来有秩序（0.812 > 0.688 > 0.625 > 0.500 > 0.438，单调），秩序诱发解释，解释诱发修改。**

正确的顺序是：**先数机制发生了几次，再决定值不值得解释。** 如果一个能力在该预算下触发 0 次，它就不可能是原因，无论分数排得多整齐。

### F2 复测：差距不存在

8 case × **4 repeats**（每 arm 32 trial，对实测差距有 90% 功效）：

| arm | repeats=2 | **repeats=4** |
|---|---|---|
| v3 完整 | 0.500 | **0.8125** |
| v3 −context | 0.812 | **0.7812** |

差值 **+0.031**（方向还反了过来），不一致 trial 7/32 分裂为 4:3，**exact McNemar p = 1.0000**。

**"v3 低于 v2"这件事本身就是一次低抽样。** v3 在 4 repeats 下是 0.8125，而 v2 在 2 repeats 下是 0.625——不存在需要解释的现象。

值得注意的是：**机制计数早就给出了同一个答案**。一个每 trial 只触发一次、预警与压缩各 0 次的能力，本来就不可能产生 0.3 的效应。那个判断在我花掉两轮实验和一次代码修改之前就已经可用了——**数机制比跑实验便宜得多，也应该排在前面**。

（按压力触发的截断作为独立的设计改进保留：无条件截断配有条件压缩这个不对称本身不合理。但它**不是**任何分数差异的原因。）

## 6. 最重要的一条：小样本结论不复现

v1 横向报告的头条是：**Claude Code 在 120s 下掉到 0.50，配对检验 p=0.031 显著**。

今天在 8-case 矩阵上，**同样的 4 条 case id、同样 120s、同样 glm-5.2**：

| | 原 4 条上的 Claude Code |
|---|---|
| v1 报告（3 repeats） | **0.50** |
| 今天（2 repeats） | **0.875** |

v1 报告自己的 bootstrap 区间是 ［0.333, 0.833］并标注"仅供参考"。**0.875 落在区间之外。**

**但差异无法归因**，而这才是真正的教训：两次运行之间，**基准仓库本身变了 22 个文件、+485 行**（扩 case 时给共享 `repo_src` 加了 8 个模块和 8 个测试文件）。采样噪声和 benchmark 内容同时移动了。

**为什么没被察觉**：实验产物只记录 suite 的**名字**。两个实验都写着 `mini_store_long`，描述的是不同的仓库。

**已修**：`suite_fingerprint` 对 case 定义 + 干净仓库全部内容做内容哈希，写进 `run_config`；`compare_experiments` 在两侧指纹不一致时拒绝静默比较。

**产品含义**：
1. **benchmark 要有版本，且版本要进结果。** 命名不是标识。
2. **扩充 benchmark 会静默作废此前所有"同一 case"的对比。** 这是扩充的固有成本，必须计入。
3. **p=0.031 的单次显著结果不足以支撑产品决策。** 本项目自己的功效模拟给出：8 case × 2 repeats 检出真实大差距的概率是 87%，×1 repeat 只有 **6%**。

## 7. 二十个测量缺陷，共同的形状

完整清单见 `README.md` 与 `PROJECT_STATE.md`。这里只讲形状：**它们几乎全部朝"更好看"的方向失败**。

| 缺陷 | 不修的话报告会说 |
|---|---|
| `--max-wall-clock` 只穿给一个 adapter 分支 | "Claude Code 不受紧预算影响"——**与真相相反** |
| 物化仓库缺 `.gitignore` | "Claude Code 8 个 trial 里 6 个工程不合规"（实为 pytest 字节码） |
| plan adherence 用模型给的 id 作键 | 报出的 0.47/0.22/0.33 全是伪影（模型会重命名 id） |
| `resume` 采纳 infra 失败的 trial | 一次限流被冻结成测量结果 |
| canary 的内容键是 Claude Code 词汇 | Cline 的每次编辑被丢弃，**canary 报"完美遵守"** |
| SWE-bench 的 editable `.pth` 压过 PYTHONPATH | 补丁全部不生效，**全员 unresolved** |
| SWE-bench PYTHONPATH 用了相对路径 | agent **全程盲改**，读起来像"benchmark 很难" |
| 丢弃匹配不上的 P2P id | oracle 被缩短，**resolved 更容易达成** |
| 被预算杀掉的 trial 报 token=0 | "该框架零 token 消耗" |
| pytest exit 4（用法错误）当成测试失败 | 0 个测试运行被读作 agent 失败 |

**没有一个是靠程序崩溃发现的。** 全部靠：金标验证、上下界检查（reference=1.00 / none=0.00）、跨框架契约测试、以及"这个数字太干净了"的怀疑。

**产品含义**：评测系统需要**自己的测试套件**，而且测的是"测量是否成立"而非"代码是否运行"。本项目 479 个测试里，相当一部分在钉住"这种失败会让分数虚高"。

## 8. 给产品方向的建议

按信心排序（前三条我有直接实测支撑，后两条是推论）：

1. **能力宣称必须绑定预算。** 脱离 wall-clock 的成功率不可比。发布时给出预算-成功率曲线，不给单点。
2. **先做 failure taxonomy，再做成功率。** 三种结构化失败可枚举、可复现、可回归，比总分更能指导迭代。
3. **假设写入面开放时模型会动测试。** 训练与评测都要按这个前提设计防护，并把防护与观测分开——挡住它就测不到它。
4. **能力配触发信号一起发布。** 没有触发时机的能力在真实预算下不会被用到，成本却照付。
5. **在解释一个差异之前，先数它的机制发生过几次。** 见 §5：本项目自己为一个触发 0 次的能力构建了两轮解释。

## 9. 这份报告本身的边界

- 全部实验为**小样本**：长程 suite 8 case，多数对比 2–3 repeats。**除 §3 的存在性观测外，没有一条比率适合直接引用。**
- 模型面窄：主要是 glm-5.2 与 glm-4.5-air，加少量 DeepSeek。跨模型族的普适性未验证。
- 真实任务面窄：SWE-bench Lite 里仅 3 条 flask 实例通过本地金标验证；requests 因依赖链已记为不可本地构建。
- §5 的两个解释都已被本项目自己的后续测量推翻，保留是为了记录过程；§6 的不复现现象**无法归因**。
- 本项目的产物**不是排行榜结果**，任何数字都不应脱离其样本量与预算被引用。
